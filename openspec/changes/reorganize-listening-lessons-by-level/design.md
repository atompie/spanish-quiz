## Context

See proposal.md - Why. Lesson id is an opaque string used as: a directory name under `public/speak/`, the `lesson` field in the auto-generated `manifest.json`, and the top-level key in the hand-authored `metadata.json`. Two code sites derive user-facing behavior from the id's shape: `LessonPicker.tsx#lessonLabel()` (display label) and `listeningSession.ts#getAvailableLessons()` (ordering). Both currently assume a purely-numeric suffix (`lesson_<digits>`), which is why `lesson_B1.1` renders incorrectly today.

## Goals / Non-Goals

**Goals:**
- Make lesson id parsing recognize the CEFR-level shape (`lesson_<LEVEL>`, e.g. `A1.1`, `B1.10`) for both labeling and ordering.
- Migrate the 19 remaining `lesson_<N>` directories and their `metadata.json` keys to the new shape, per the mapping in proposal.md.
- Keep the fallback behavior (raw id shown) for any id that doesn't match the recognized shape, so a malformed/legacy id never crashes the picker.

**Non-Goals:**
- Do not touch `dist/` (build output, regenerated by build).
- Do not add a `level` field to the runtime data model or use `metadata.json`'s existing (currently unused, inconsistently-typed) `level` property — the level is derived purely from the id string.
- Do not build a migration path for existing `localStorage` "completed lesson" markers — accepted as reset per the answered question.
- Do not change how `manifest.json` is produced (it stays auto-generated by `scripts/generate-speak-manifest.ts` / the dev-server plugin).

## Decisions

- **Parse level from the id with a single regex, reused by both label and sort.** Introduce one helper, e.g. `parseLessonLevel(lesson: string): { level: string; major: number; minor: number } | null` in `listeningSession.ts`, using `/^lesson_([ABC])([12])(?:\.(\d+))?$/`. Both `lessonLabel()` and `getAvailableLessons()` call it instead of each having their own regex, so the accepted id shape can't drift between labeling and sorting.
  - Alternative considered: keep two independent regexes (current state). Rejected — that's exactly how the display bug happened (the sort regex and the label regex already disagree today), and duplicating the pattern risks the same class of bug again.
- **Sort key = (CEFR level rank, sublevel digit, sequence number).** Level rank order is `A < B < C`; within a level, sublevel `1 < 2`; within a sublevel, sequence number is compared numerically (defaulting to `0`/absent when there's no `.N` suffix) so `A1.2` sorts before `A1.10`. Legacy purely-numeric ids (`lesson_<digits>`, none should remain after migration, but keep the fallback) sort by their number, before any CEFR-shaped id — preserves current behavior for anything not yet migrated.
  - Alternative considered: generic natural-sort (e.g. split on digit runs and compare piece-wise) applied to the whole string. Rejected as needlessly generic — the id shape is a known, closed CEFR pattern, not arbitrary user text, so an explicit parsed sort key is clearer and easier to test.
- **Migrate directories with a plain rename script/commands, not new tooling.** This is a one-time content migration (19 directories), not a recurring operation, so a short one-off shell loop (`git mv` per directory) plus manual `metadata.json` key edits is sufficient — matches how `lesson_2` -> `lesson_B1.1` was already done by hand. No new script is added to `scripts/`.
- **Regenerate `manifest.json` via the existing generator after renaming**, rather than hand-editing it, since it's already a scan of `public/speak/` (`scripts/generate-speak-manifest.ts`) and hand-editing risks drifting from the real directory contents.

## Risks / Trade-offs

- [Renaming directories loses git history for those paths under a plain `mv`] → Use `git mv` for each of the 19 renames so history is preserved as a rename instead of delete+add (the earlier `lesson_2` -> `lesson_B1.1` move was a plain `mv` and shows as delete+add in git status; the remaining 19 can do better).
- [`metadata.json` key renames done by hand risk a typo that silently breaks one lesson (its `parts` would just be empty because the manifest `lesson` field no longer matches the metadata key)] → After migration, manually cross-check every `manifest.json` `lesson` value has a matching `metadata.json` key (e.g. `jq` diff of the two key/value sets) before considering the migration done.
- [Existing `localStorage` "completed" markers for the 19 renamed lessons become orphaned] → Accepted per proposal.md; no mitigation needed (non-critical, per-browser, user can re-mark).

## Migration Plan

1. For each of the 19 directories, `git mv public/speak/lesson_<old> public/speak/lesson_<new>` per the mapping in proposal.md.
2. Rename the matching top-level key in `public/speak/metadata.json` for each of the 19 lessons (same mapping).
3. Regenerate `public/speak/manifest.json` by running the existing generator script (`scripts/generate-speak-manifest.ts`) or starting the dev server (which runs the equivalent Vite plugin).
4. Implement `parseLessonLevel()` in `listeningSession.ts`, and use it from `getAvailableLessons()` for sorting.
5. Update `LessonPicker.tsx#lessonLabel()` to use `parseLessonLevel()` for the CEFR case, keeping the raw-id fallback for anything unmatched.
6. Manually verify in the running app: the lesson list shows `"Lesson A1.1"` .. `"Lesson A1.19"` and `"Lesson B1.1"`, in that order, each linking to working audio.

No rollback beyond `git revert` is needed — this is a content/display-only change with no server-side state.
